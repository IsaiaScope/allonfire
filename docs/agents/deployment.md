# Deployment

VPS, Docker services, CI. Pictures: `images.md`.

- VPS: Hetzner, 4 vCPU / 8 GB RAM, no swap, at 188.245.174.30 (ssh main-vps)
- Observability: self-hosted OpenObserve (`telemetry`, Production and Local; UI at `observe.isaiariva.com` behind its own login only (a basic-auth gate loops on it), OTLP ingest internal only) + Umami (Local only so far) — see `docs/adr/0006-self-hosted-observability.md`. Production's `telemetry-init` gives OpenObserve its own storage user, limited to the `telemetry` bucket
- Redis: production's `redis` service (internal network only, 128 MB, append-only) serves the Apps; Dokploy's own `dokploy-redis` is never shared
- Orchestrator: Dokploy runs one compose project of GHCR images; `.github/workflows/deploy.yml` builds only the affected Deploy units on a push to `prod` and redeploys it (ADR 0018).
- DB: Shared PostgreSQL 16 (database: allonfire)
- Proxy: Traefik with Let's Encrypt SSL
- A Docker service, its container (`allonfire-<name>`), its volume and its hostname are named after its purpose, never its software: `database`, `redis`, `storage`, `image-server`, `cdn` (the public delivery address, nginx: pictures under `/image` go to `image-server`, any other path is a 404 until something lives there), `workflow`, `telemetry`, `analytics`, and `<name>-init` for a one-shot (`docker-compose.dev.yml`, `docker-compose.prod.yml`; `packages/config/local/tests/service-names.test.ts` fails on an old name). Swapping the software is an `image:` line.

- Removing a feature sweeps its deploy and CI config in the same change: the Dockerfile's args and stubs, `deploy.yml`'s build-args, `ci.yml`'s env, turbo's task `env`, the Playwright build step, the compose comments, the `.env.example` lines, and the GitHub secret once no workflow reads it (`local-files.test.ts` guards the Back Office build's storage leftovers).
- Back Office build needs `BACK_OFFICE_URL`, its own public address (`metadataBase`): a Docker build arg (`deploy.yml`) and a CI secret for the `build` job, each read from its GitHub environment (`prod`, `dev`) under the same name, and the same value at runtime (`docker-compose.prod.yml`).
- Before the API starts, the one-shot `storage-setup` service (the API's image) creates the `image` bucket when missing and keeps it closed (an earlier read-only policy is removed); it uploads no Images.
- CI runs check-types, test and build with `turbo --affected`; lint and the repo-wide checks always run. Affected is Turbo's (`futureFlags.affectedUsingTaskInputs`): every task's `inputs` excludes `**/*.md`, so a Markdown-only change affects nothing, and a root `package.json`, `turbo.json` or lockfile change affects everything; a new task needs the same exclusion. `pnpm ci:affected <base>` (`@allonfire/core/features/ci/affected`) reads `turbo query affected --packages` as the affected Apps (packages under `apps/`) and Deploy units; `docker/`, `.dockerignore` and `pnpm-workspace.yaml`, which no task reads, reach every unit. A push to `prod` diffs against the `deployed/prod` tag, the last commit that deployed.

- Production values live in git-ignored `.env.production` files, one beside each `.env` and in the same shape: the tracked `.env.example` beside it is the template for both, and a production-only key sits there commented out. A Next App's sits in its `env/` folder, since `next build` loads a `.env.production` in the App's root. Every `.env`, `.env.development` and `.env.production` names exactly the keys of its `.env.example`, commented out where unused, in its order. An example lists exactly the keys its reader takes (the zod env schemas, or the compose files for `docker/`), in blocks by owner with keys in alphabetical order (`local/tests/env-examples.test.ts`). `docker/.env.production` is Dokploy's whole AllOnFire env (every key the prod compose reads) plus `DOKPLOY_*` for GitHub `prod`; an App's build-time keys are GitHub `prod` secrets; the App and package files record what the compose gives each service, so a secret can sit in more than one: rotate it in every file that names it. Read one only through `pnpm env:prod` (`packages/config/local/env-production.sh`), which never prints a value: `keys <file>` lists the names, `check <file>` names each empty key (exit 1), `copy <file> <key>` puts a value on the clipboard for a Dokploy paste, `gh-secret <file> <key> <env>` pipes it into `gh secret set`. Never `cat`, `grep` or open one.
- Compose reads `.env` beside the compose file (`docker/.env`, from `docker/.env.example`), never the repo root's: the `POSTGRES_*` there are the database service's own variables, named by the Postgres image.
- `deploy.yml` reaches Dokploy's API through `panel.isaiariva.com`'s basic auth: `DOKPLOY_URL` (a `prod` secret) carries the `main-github-deploy` login, and `DOKPLOY_API_KEY` is the Dokploy key of the same name. Dokploy's keys carry better-auth's per-key limit (10 requests a day unless set), so each key is created with `rateLimitMax: 200`: one deploy makes up to 92 calls (the deploy, then a poll every 10 s for 15 minutes).

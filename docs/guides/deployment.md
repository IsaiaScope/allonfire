# Deployment

AllOnFire's delivery: Docker services, CI, deploys. Pictures: `images.md`. The server itself: `vps.md`; security: `vps-security.md`; backups and disaster recovery: `vps-backups.md`.

- VPS: Hetzner, 4 vCPU / 8 GB RAM, no swap, at `<vps-ip>` (`ssh main-vps`; `vps.md`)
- Observability: self-hosted OpenObserve (`telemetry`, Production and Local; UI at `observe.isaiariva.com` behind its own login only (a basic-auth gate loops on it), OTLP ingest internal only) + Umami (Local only so far) — see `docs/adr/0006-self-hosted-observability.md`. Production's `telemetry-init` gives OpenObserve its own storage user, limited to the `telemetry` bucket, where it keeps 14 days of data. The API and the Back Office send OTLP to `http://telemetry:5080/api/default` (`TELEMETRY_ENDPOINT`, a plain value in the prod compose) with `TELEMETRY_HEADERS`, the `Basic` header of an OpenObserve ingestion token (IAM, Ingestion Tokens), one key for both, under their own `TELEMETRY_SERVICE_NAME`. The API's log lines ship through a pino transport, the Back Office's through its OpenTelemetry SDK (`next-apps.md`). Production's compose requires `TELEMETRY_HEADERS` (`:?`): the deploy fails without it. Local and tests run without telemetry while the keys are unset
- Redis: production's `redis` service (internal network only, 128 MB, append-only) serves the Apps; Dokploy's own `dokploy-redis` is never shared
- Orchestrator: Dokploy runs one compose project of GHCR images; `.github/workflows/deploy.yml` builds only the affected Deploy units on a push to `prod` and redeploys it (ADR 0018).
- DB: Shared PostgreSQL 16 (database: allonfire)
- Hosts: every `isaiariva.com` record on the VPS is proxied through Cloudflare (free plan, SSL/TLS Full (strict)): `back-office.`, `api.` and `cdn.` serve the Apps; `storage.` and `database-console.` sit behind the `admin-gate@file` basic auth, `sofia.` behind its own `sofia-gate@file`, `panel.` (Dokploy) behind `panel-auth@file`, `observe.` behind its own login; `board.`, `workflow.`, `monitor.` and `www.` are other services; the bare domain redirects to `www.`; `laura.` waits for Laura's rebuild. A record on another server (a media server, say) stays DNS only: Cloudflare's CDN terms bar serving mostly audio or video without its paid services. Cloudflare's Cache Rule `cdn: no edge cache` bypasses its cache on `cdn.`: imgproxy answers with `Cache-Control: public, max-age` up to a link's expiry (a year for a public Image), and an edge copy would keep serving a deleted or private picture; `cdn`'s nginx keeps the resizes and checks each with imgproxy every second.
- Proxy: Traefik with Let's Encrypt (HTTP-01 on port 80; Cloudflare's Always Use HTTPS leaves `/.well-known/acme-challenge/` alone, so renewal works through the proxy). `websecure`'s `forwardedHeaders.trustedIPs` lists Cloudflare's ranges, so `X-Forwarded-For` reaches a service as `visitor, Cloudflare`: the API reads it with `API_TRUSTED_PROXY_HOPS=2`, and `sofia-ratelimit` with `ipStrategy.depth: 1`.
- Firewall: Hetzner's `vps-firewall` lets only Cloudflare's ranges reach 80 and 443; SSH (`<ssh-port>`) and ICMP are open. Cloudflare's ranges (`cloudflare.com/ips-v4`, `ips-v6`) change rarely; when they do, update the firewall and `trustedIPs` together.
- A Docker service, its container (`allonfire-<name>`), its volume and its hostname are named after its purpose, never its software: `database`, `redis`, `storage`, `image-server`, `cdn` (the public delivery address, nginx: pictures under `/image` go to `image-server`, any other path is a 404 until something lives there), `workflow`, `telemetry`, `analytics`, and `<name>-init` for a one-shot (`docker-compose.dev.yml`, `docker-compose.prod.yml`; `packages/config/local/tests/service-names.test.ts` fails on an old name). Swapping the software is an `image:` line.

- Removing a feature sweeps its deploy and CI config in the same change: the Dockerfile's args and stubs, `deploy.yml`'s build-args, `ci.yml`'s env, turbo's task `env`, the Playwright build step, the compose comments, the `.env.example` lines, and the GitHub secret once no workflow reads it (`local-files.test.ts` guards the Back Office build's storage leftovers).
- Back Office build needs `BACK_OFFICE_URL`, its own public address (`metadataBase`): a Docker build arg (`deploy.yml`) and a CI secret for the `build` job, each read from its GitHub environment (`prod`, `dev`) under the same name, and the same value at runtime (`docker-compose.prod.yml`).
- Before the API starts, the one-shot `storage-setup` service (the API's image) creates the `image` bucket when missing and keeps it closed (an earlier read-only policy is removed); it uploads no Images.
- CI (`.github/workflows/ci.yml`) runs one job per Stage (`testing.md`): `static`, `test`, `e2e` and `build`, each its Stage's command with `--affected --keep-going`, in parallel; `build` alone waits for `static` (`needs: static`), being the one job given the real `dev` secrets, and `e2e` runs only when the `affected` job finds an affected App or a changed package with browser tests. Every Stage job shares `.github/actions/prepare` (setup, then the Prisma client) and writes its table to the run's summary page; `affected` writes what each Stage covers on the run and why e2e would not. The required checks on `dev` and `test` are the Stage jobs (`static`, `test`, `e2e`, `build`; `test` also requires `Verify Source Branch`). `--affected` narrows Turbo's tools (types, tests, builds); lint, knip and jscpd always read the whole repo. Affected is Turbo's (`futureFlags.affectedUsingTaskInputs`): every task's `inputs` excludes `**/*.md`, so a Markdown-only change affects nothing, and a root `package.json`, `turbo.json` or lockfile change affects everything; a new task needs the same exclusion. `pnpm ci:affected <base>` (`@allonfire/core/features/ci/affected`) reads `turbo query affected --packages` as the affected Apps (packages under `apps/`) and Deploy units; `docker/`, `.dockerignore` and `pnpm-workspace.yaml`, which no task reads, reach every unit. A push to `prod` diffs against the `deployed/prod` tag, the last commit that deployed.
- A toolchain pin (pnpm version, setup steps, action versions) is declared once (package.json packageManager, one composite action, one Dockerfile base stage) and read everywhere. A workflow job sets up through `.github/actions/setup` (pnpm, Node from `package.json` with the pnpm cache, `pnpm install --frozen-lockfile`) after its own `actions/checkout` step (`fetch-depth: 0` where it diffs): GitHub reads a local action from the checkout, so checkout cannot move into it.

- Production values live in git-ignored `.env.production` files, one beside each `.env` and in the same shape: the tracked `.env.example` beside it is the template for both, and a production-only key sits there commented out. A Next App's sits in its `env/` folder, since `next build` loads a `.env.production` in the App's root. Every `.env`, `.env.development` and `.env.production` names exactly the keys of its `.env.example`, commented out where unused, in its order. An example lists exactly the keys its reader takes (the zod env schemas, or the compose files for `docker/`), in blocks by owner with keys in alphabetical order (`local/tests/env-examples.test.ts`). `docker/.env.production` is Dokploy's whole AllOnFire env (every key the prod compose reads) plus `DOKPLOY_*` for GitHub `prod`; an App's build-time keys are GitHub `prod` secrets; the App and package files record what the compose gives each service, so a secret can sit in more than one: rotate it in every file that names it. Read one only through `pnpm env:prod` (`packages/config/local/env-production.sh`), which never prints a value: `keys <file>` lists the names, `check <file>` names each empty key (exit 1), `copy <file> <key>` puts a value on the clipboard for a Dokploy paste, `gh-secret <file> <key> <env>` pipes it into `gh secret set`. Never `cat`, `grep` or open one. To rotate a value: change it in every `.env.production` that names it, `copy` it into Dokploy's env and redeploy the compose, and `gh-secret` it into GitHub when a workflow reads it.
- Compose reads `.env` beside the compose file (`docker/.env`, from `docker/.env.example`), never the repo root's: the `POSTGRES_*` there are the database service's own variables, named by the Postgres image.
- `deploy.yml` reaches Dokploy's API through `panel.isaiariva.com`'s basic auth: `DOKPLOY_URL` (a `prod` secret) carries the `main-github-deploy` login, and `DOKPLOY_API_KEY` is the Dokploy key of the same name. Dokploy's keys carry better-auth's per-key limit (10 requests a day unless set), so each key is created with `rateLimitMax: 200`: one deploy makes up to 92 calls (the deploy, then a poll every 10 s for 15 minutes).
- Branches cascade feature → `dev` → `test` → `prod`, by PR: `ci.yml` runs on a PR to `dev` or `test`, `ci-branch-gate.yml` fails a PR to `test` not from `dev` and one to `prod` not from `test`, and only a push to `prod` deploys (`.github/workflows/`; the `/allonfire-deploy` command, `.claude/commands/allonfire-deploy.md`, walks it). (`docs/superpowers/specs/2026-04-04-allonfire-deploy-command-design.md`)
- `deploy.yml` builds each image natively on GitHub's arm64 runner as `:<sha>`, moves `:prod` only once every image exists, refuses a re-run whose commit is behind `deployed/prod`, and on a manual run (`workflow_dispatch`, from `prod` only) deploys every unit: `.github/workflows/deploy.yml`.
- Production starts in order `db-backup` → `db-migrate` → `storage-setup` → `api` (healthy) → `back-office`, every image `pull_policy: always`; Laura is out of Production until its rebuild: `docker/docker-compose.prod.yml`.

# Back Office

How the Back Office (`apps/back-office`) builds its pages. General Next rules: `next-apps.md`.

## Every page's plan answers the data checklist

The checklist (TanStack Query over the private cache, both copies refreshed, resource protection, resource changed, lost and gone) is general to every Next App: `next-apps.md`, "The data checklist". A Back Office plan names each point, task by task.

How the Back Office differs from any Next App (frame, Sections, signed-out pages, Home cards, Services). Everything every App shares (the private cache and its checklist, signed-in pages, page information and special pages, brand and PWA, environment) is in `next-apps.md`.

## Back Office specifics

- the signed-in frame is `(signed-in)/layout.tsx` (ADR 0024), shadcn's `sidebar-07` (`features/navigation/components/app-frame`: a sidebar collapsing to icons, a drawer on a phone, no tab bar; the App switcher over `enterableApps`, each App's address from the env, `LAURA_URL` optional; the account menu; a breadcrumb header): static, drawn from the App's Sections (`features/navigation/constants/sections`, an explicit tuple: Biome sorts object keys), which the proxy's sign-in gate and a guard test also read. A new Section is one row there plus its page; its UI state is a typed nuqs param read on the client, never a cookie the server reads
- a Section's page is `SectionPage` (`features/navigation/components/section-page`): `width="full"` (the default) for a list or a table, `width="form"` for a form (centred, capped at `max-w-4xl`, a container: its layout switches on its own width, `@2xl:` for two columns, never on the screen's, since the sidebar decides how much room the page has)
- the signed-out pages (Sign in, Forgot password, Reset password, Email verified) wear one frame, `TicketGate` (`features/auth/components/ticket-gate`); each takes the App's address (`BACK_OFFICE_URL`) from its page, never from the env inside the component. Sign in posts `callbackURL` (`/email-verified`), where a verification link lands; the page (`EmailVerified`) reads its outcome (Better Auth's `error` query parameter) in the browser, so it stays static, and leads back to Sign in. The reset token is read the same way. The password rules (`shared/components/password-rules`, `shared/utils/password-checks`) are shared by the User forms and Reset password.
- a Section can list its own pages (`pages` in `features/navigation/constants/sections`, each with its icon): the sidebar draws them as `sidebar-07`'s collapsible sub-menu (`SidebarSectionLink`), indented with no rule beside it and sliding open, the whole row opening it, open while you are on one, and only the page you are on marked, never the row; folded to icons the row links to the first page. The Section's own page opens the first (`sectionEntry`), and the breadcrumb adds the page after the Section. Services is the first: its pages are its Services (Mail).
- the Services Section (`features/services`) reads the providers like Users: the page hydrates them through `servicesHydration(type)` (kept in the visitor's browser only, `"use cache: private"` under `SERVICES.CACHE.TAG` and the type's own `serviceTag`, with its own life in `SERVICES.CACHE.LIFE`; dehydrated inside the cache) into `ServiceProviders`, a client component that reads them back with `useQuery(servicesQuery(api, type))` under `QUERY.SERVICES.LIST(type)`, `staleTime: "static"`, so it is asked again only by an action, never on a clock; the API is asked for that type only, `?type=`, so one type's page never calls another type's vendors; every Services action clears the server's copy with `updateTag` (a type's own action, the Service switch, that type's tag, and one that cannot say its type, a provider's, every type's) and the browser's with `useRefreshServices` (`invalidateQueries` on `QUERY.SERVICES.ALL`): after a test send, a saved provider, a saved switch, and a save refused as changed or removed, so the Admin's own change is never stale; another Admin's change or mail sent elsewhere shows after the kept copy's 5 minutes, on a reload or a navigation, not live; what a provider's API reports reaches the rings late (the API's 30 seconds, the vendor's own delay, which for a Resend-shaped provider is up to ~10 minutes, this browser's 5 minutes), a provider that cannot report draws empty rings and an error toast); `PROVIDER_CARD` in `ServiceProviders` draws each Service type's providers, a new type adds its card; each provider is one AOF form on its Version, its switches Gooey choices like the Roles, no host or login field (the environment holds where a provider is reached), no delete, and a test send that goes to the signed-in Admin's own address.
- Home shows the Users overview above Storage (`features/users`: `UsersOverview`, inside Home's `HomeSection` and core's `AOFHydratedBoundary`), read the same way as Storage and answering the data checklist: `usersOverviewHydration()` (`"use cache: private"` under the Users' own `USERS.CACHE.TAG` and `LIFE`, so `addUser`, `editUser` and `deleteUsers` drop it with the list) fills a client view that reads it back with `useQuery(usersOverviewQuery(api))` under `QUERY.USERS.OVERVIEW` (inside `QUERY.USERS.ALL`, so the Users mutations refresh it), `staleTime: "static"`. The API route is `GET /v1/user-usage/overview` (a Back Office Admin read now). One card: the total as a badge and a horizontal chart of Users and Admins per App (`AOFBarChart` with `wholeValues`); a User in two Apps counts in both, one in none only in the total. A first read that fails and a 403 each draw a card of the chart's size (`OverviewFailed`, `OverviewForbidden` in `shared/components/overview-card-state.tsx`; Users keeps its title), the failure with a retry button, the Japan blue brushed 再, the 403 with its words and no retry; neither toasts.
- Home shows the Storage overview (`features/storage`), read like Users and Services and answering the data checklist (`next-apps.md`): `storageOverviewHydration()` (`"use cache: private"`, `STORAGE.CACHE.TAG`, `STORAGE.CACHE.LIFE`, never under 5 minutes) fills `StorageOverview` through core's `AOFHydratedBoundary` (`features/next/query/components`: the read never throws past it, a refusal is left to the view), a client component that reads it back with `useQuery(storageOverviewQuery(api))` under `QUERY.STORAGE.OVERVIEW`, `staleTime: "static"`, one retry after a server failure and none after a refusal. The API (`GET /v1/storage/overview`, a Back Office Admin read now) keeps the bucket listing 5 minutes in Redis, and every write that moves the bucket (an Image upload, change or delete; an Avatar stored or removed; Users deleted with theirs) drops it through the module's `changed` dep (`ImageDeps`, `UserDeps`) before answering, so the refetch that follows lists again and the Avatars (the listing minus the database's Image bytes) never set a fresh sum against a stale one; only a change made outside the API (a file put in the bucket by hand) can trail by the 5 minutes. The page is read-only, so it has no Version: every write that moves the bucket drops this browser's copy (`updateTag(STORAGE.CACHE.TAG)` in the Image delete, the Users delete and the Edit User action when an Avatar was sent; `QUERY.STORAGE.ALL` invalidated by the Images and Users delete mutations; a new action that changes files in the bucket does the same, in all three layers), and another Admin's change shows after the kept copy's 5 minutes. Home draws each Section's heading at once and only its card waits behind a skeleton: whoever the page check lets in is an Admin of the Back Office (its `minRole` floor in `ACCESS.APP_SETTINGS`, pinned by a test in `access.test.ts`), so Home has no Admin check of its own, as no other Section has (lower that floor and Home needs a gate again); a 403 that still comes (a Session that lost its Role meanwhile) draws a card that says so, with no toast, as every state of a Home card does through ui's `AOFQueryView` (`next-apps.md`; Storage's cards have no title line, since its buckets are only known with the data); a bucket the API could not list leaves its card's error line and keeps the chart (per App, a line of public Image bytes, one of private and one of Avatars: the Images' from the database, an Image in several Apps counting in each; the Avatars' from the API, which lists the Avatar files fresh, by their prefix, and counts each User's file in every App they are in). Home is a list of bucket cards (`BucketCard`): each is titled by the bucket's name and shows its files and size as badges, each in its own chart-token tint (a size reads through core's `formatSize`: MB, then GB, TB past 1024, two decimals, the same everywhere); `BUCKET_VIEW` (`constants/buckets.ts`) gives a bucket's kind its mark and kanji and `DETAILS` in `bucket-card.tsx` what only that kind adds (the API names each bucket's `kind`, `STORAGE_USAGE.BUCKET_KIND`, apart from its configured name, so a card never depends on `STORAGE_BUCKET`) (the Images' chart, `AOFBarChart` in `packages/ui`: horizontal, three lines per App, so more Apps grow it down the page), so a new kind is an entry in each plus a line in the API's list of buckets.
- a Section owns every page under its path (`/users/<id>`): `isCurrentSection` and the proxy's sign-in gate match `<path>/` as a prefix, never for Home (`features/navigation/utils/sections`). (`docs/superpowers/specs/2026-10-21-back-office-users-list-design.md`)
- a User's Version covers `updatedAt` and every (App, Role) pair, so a Membership gained or removed elsewhere is never overwritten by a save of the User's other fields (`versionOf` in `features/users`)
- the Images Section's Add and Edit pages (`/storage/images/new`, `/storage/images/[id]`, `features/images`) follow Users' `new`/`[id]`: `AddImage` takes up to `IMAGE.LIMIT.FILES_PER_UPLOAD` pictures at once, each a row (preview, alt, access, Apps) seeded from a shared set at pick time, and sends them in one all-or-nothing `POST /images` through the `addImage` server action; `EditImage` saves one `PATCH /images` item on the `version` it opened with and hosts the single-Image delete. Both go through `ImageAltFields`, `ImageAccessRow` and `ImageAppsRow` (field groups, `image-form-parts`, `image-alt-fields`): alt is a field per language the Image holds (English and Italian always, any other of core's catalogue through the "Add a language" picker), and the form sends the whole `alt` since the API replaces it. The Add page offers only the Apps the visitor administers (`administeredApps`); the API stays the judge. Both actions clear `IMAGES.CACHE.TAG` and `STORAGE.CACHE.TAG`, the form then `invalidateImages` (`QUERY.IMAGES.ALL`, `QUERY.STORAGE.ALL`) before it opens the list (`useToastThenList`). A form field that is no input of the API (`picker`, `shared`, a row's `id`) is the form's own: the schema lets it through, the action ignores it. (`docs/superpowers/specs/2026-11-13-storage-images-add-edit-design.md`)
- the Back Office raises Next's Server Action body limit (1 MB) to `IMAGES.UPLOAD_BODY_LIMIT` (the API's `UPLOAD_BYTES` plus 1 MiB) in `next.config.ts`: the Add Images form posts a whole upload through an action. A deployment's ingress must let a body that size through to the Back Office.

# Stored pictures

Images and Avatars: storage, the image server, signed links, how a page shows them (ADR 0027).

- Give images explicit dimensions, or use `fill` inside a sized container, to prevent layout shift.
- Every stored picture shown in a Next App (an Image, an Avatar, wherever it appears: a table, a card, the account menu) shows its blur while it loads, as `/storage/images` does, except a tile under 40 px, where next/image warns against any placeholder and the initial stands in: an Image through `AOFStorageImage` (`placeholder="blur"`), an Avatar through `UserAvatar` (`tileBlur`). A new place that shows one carries the blur the API answers beside it (`blurDataUrl`, `imageBlurDataUrl`), never a bare `AOFImage`/`<img>`.
- Every stored picture (Images and Avatars) sits in the `image` bucket, closed: nobody reads it anonymously. It reaches a browser only through the `cdn` service, under `/image` (nginx, the public delivery address: `cdn.isaiariva.com` in Production, `localhost:9010` Locally; it keeps each answer, keyed on the whole link plus the format `Accept` picks, and serves it again only after asking imgproxy with its ETag once it is over a second old: imgproxy checks the link and the file, 304 without resizing, 404 once expired or deleted, so a dead link dies within `IMAGE_SERVER.CACHE_CHECK_SECONDS`; its config is inline in both compose files, kept identical by `service-names.test.ts`, since Production mounts no file) in front of the `image-server` service (imgproxy, `IMGPROXY_KEY`/`_SALT` from `STORAGE_IMAGE_SERVER_KEY`/`_SALT`; it reads only `s3://image/`, `IMGPROXY_ALLOWED_SOURCES`, Local also a test run's `allonfire-test-` buckets; Production at `https://${CDN_HOST}/image`), by links the API signs (`@allonfire/storage/features/image-server/sign`: `pictureLink`, `pictureSrcSet`, `privateLinkExpiry`): a public Image's never expire; a private Image's and an Avatar's expire at the end of the hour after the next (`ceil(now / 1h) * 1h + 1h`), and only those the API lets see the picture get them. A public Image made private moves to a new file, so its public links die at once; one another request makes public meanwhile answers 409 `IMAGE_CHANGED` rather than turn private in place. The User module's `PUT`/`DELETE /users/:id/avatar` set and remove an Avatar; `User.image` holds its file's name (`avatar-<userId>-<uuid>.avif`), signed on every read (the list, the Session's `customSession`), or a provider's `https://` picture as it is; Google's `overrideUserInfoOnSignIn` stays off. In a page, a stored picture uses its signed links, never the App's optimizer: an Image's through `srcSetLoader` (`@allonfire/ui/shared/utils/image-server-loader`), an Avatar's one link `unoptimized` (a loader that ignores the width makes next/image warn), its blur through ui's `tileBlur` (`features/image/utils/tile-blur`: the data URL as the `placeholder` from 40 px, none under; never `placeholder="blur"` on a tile told a small `width`, which next/image's 20px SVG blur turns see-through); a provider's picture goes through the optimizer, allowed by auth's `withProviderPictures` (a new provider adds its host to `AUTH.PICTURE_HOSTS` first, or next/image refuses it and a dev page breaks).
- Storage side effects that must be undone on failure run with Promise.allSettled and clean up every success through deleteLeftovers; never Promise.all.
- An Image travels with its Version (`Image.version`, ADR 0028): each `PATCH /images` item carries it, and an Image changed since, or one the batch would leave in no App, answers 409 `RESOURCE_CHANGED` with nothing written; an Avatar's `PUT` (form field) and `DELETE` (JSON body) carry the User's `version` the same way.
- Image alt: a write needs every Base language; a read goes through `readAlt` (a missing language reads as English, else the first with text; a stored `""` stays `""`, decorative): `packages/database/src/features/image/utils/alt.ts`. (`docs/superpowers/specs/2026-10-02-aof-image-hardening-design.md`)
- An Avatar's HEIC becomes a JPEG in the browser before cropping: Safari draws it, other browsers load `heic-to` only when needed: `packages/ui/src/features/form/avatar-field/utils/heic-to-jpeg.ts`. (`docs/superpowers/specs/2026-10-27-user-avatar-design.md`)
- A bulk `DELETE` (`/images`, `/users`) is idempotent: an id that is not there, or an Image the caller cannot see, is skipped as already gone (no 404, so a retry or a second Admin's race is safe, and a refusal never tells which ids exist); the answer is `200 {deleted}` with the count that really went, and the host is told the bucket changed only when `deleted > 0`. An Image the caller sees but may not delete still answers 403 for the whole batch. Back Office toasts `done`, `gone` or `partly` from `asked - deleted`.
- Preparing, storing and signing pictures, Avatars, the Image module (`ImageDeps`, access, errors, limits), bucket setup, test buckets, the storage env: `packages/storage/README.md`.
- The Image endpoints, their guards and limits: `apps/api/README.md`.

- The Back Office's Home shows how much the `image` bucket holds (objects and bytes, Avatars included) and the Images' public and private bytes per App: `GET /v1/storage/overview` (`apps/api/src/features/storage-usage`, bucket listing from `imageBucketTotals` kept 5 minutes in Redis, Image figures from `imageStats`). See `back-office.md`.
- The Images list's filters live in one `search` param like Users (ADR 0026): `?search=app:laura,back_office access:public input:sea`. `IMAGE.SEARCH` (`@allonfire/storage/features/image/constants/image`) reads and writes it for the API (`GET /v1/images`, beside the `app` query an App's own page asks with) and the Back Office (`imagesParams`, `ImagesToolbar`, `ImagesFilters`); the text matches the alt in either language or the file name; a field or value it does not know is dropped. The `/storage/images` table lists Image rows only: Avatars (User pictures) have no row there and are counted only in the Home overview.

# Service quotas and transactional mail

**Goal:** Give the Back Office control over shared services and their providers, and support Better Auth verification and password reset through quota-aware transactional email, without opening Registration in any App.

**Status:** implemented (uncommitted) @ 2026-11-03T17:32:31Z

This is a planning artifact; implement with `/iso-write` only after review. The user chose a generic Service with an id and name such as `MAIL`, provider name, enabled state, daily limit and usage, managed in the Back Office. Provider secrets belong in environment variables indexed by slot; non-secret configuration belongs in the database. Use enabled providers in slot order, filling each one's quota before the next. On an uncertain SMTP outcome, stop rather than automatically try the next provider, as the user confirmed.

## Decisions and boundaries

- A Service is a shared operational capability, not an App or the API. Keep its name distinct from the existing glossary's use of “service” for implementation and Docker; settle final domain vocabulary during implementation. `MAIL` is the first capability; do not implement speculative other capabilities.
- Plan for Brevo (slot 0) and Resend (slot 1) free tiers in that provider order, subject to current terms. SMTP2GO is skipped for now: its sign-up refuses a Gmail address and asks for one at the owner's own domain; it can join later as another slot. Configure safety limits no higher than the applicable free allowance; disable paid overages in provider accounts when available. Brevo currently lists 300/day, Resend 100/day and 3,000/month. Recheck all limits, reset windows and account restrictions during setup. No guarantee of permanent free service.
- Provisioned 2026-11-03, both named `allonfire-api`: a Brevo SMTP key (Standard variant, "No expiration", but Brevo still deactivates any key after 90 days without use; login and host shown in Brevo's SMTP & API settings, `smtp-relay.brevo.com:587`) and a Resend API key with Sending access only (the SMTP password for `smtp.resend.com`, user `resend`). The owner copied the values; they were never read by an agent and live only in env. Brevo's SMTP keys do not block unauthorized IPs yet: allow the VPS IP under Brevo's Security, Authorized IPs, then activate blocking. Resend sends to other people only from a verified domain (one on the free plan).
- Use the owner's selected no-reply address at the deployment domain as the sender, configured outside this public repository (`<sender-address>` in examples). Verify the domain with both providers and test each independently. Inspect existing DNS and mail configuration before changes; reconcile SPF, DKIM, DMARC and return-path records without disrupting existing services. A sending address does not itself provide an inbox.
- Build email templates with React Email behind reusable AOF email components in the shared UI package. Provide a shared AllOnFire default and an explicit per-App customization seam for branding and content; Apps select their own design without the mailer importing an App. Use the requesting App's language when available and fall back to English when it is missing or unsupported; use the shared AllOnFire design if App context is missing. Keep email rendering server-only and preserve package boundaries. Start with verification and password reset, HTML and plain text, and Base languages. Do not expose tokens in logs or preview data.
- Model Service identity and enabled state, provider records linked to a Service (name, unique credential slot, enabled state, non-secret SMTP connection and sender configuration, configurable daily and optional monthly limits), and separate per-provider usage records for each quota window. Show daily and monthly usage, limits, resets and effective availability on the Service; don't store a derived paused state. Enforce uniqueness and valid nonnegative limits in the database and application.
- Numbered `MAIL_PROVIDER_<slot>_*` environment entries hold secrets only; a database row selects the matching slot. Adding a new secret requires deployment; selecting or editing non-secret configuration does not. Never expose secrets to the API client, logs, test snapshots or the Back Office. Validate missing credentials and show an actionable unavailable state.
- An atomic database reservation before SMTP handoff is the hard ceiling, including simultaneous API instances. Reserve per provider and quota period; a read-only precheck can improve errors but cannot guarantee availability. Count a reservation until acceptance or definite failure; release only when it is known that the provider did not accept the message. Uncertain outcomes remain counted and are not retried through another provider, to avoid duplicates. A process crash can conservatively consume capacity; document and expose this as reserved/attempted usage, not confirmed delivery. SMTP acceptance is not inbox delivery.
- Enforce every configured quota window for a provider together, including both daily and monthly windows for Resend. Reserve all applicable windows atomically before sending, so a concurrent request cannot bypass either limit; a provider becomes exhausted when any applicable window is full. The configured thresholds cannot account for sends made outside this system, so monitor provider-side usage and account settings too.
- Mail from these provider accounts is intended to be sent only by AllOnFire. Record each quota window's provider, period type, limit, reset rule and time zone (or other provider-specific boundary where necessary) and keep per-window usage; show current counts and next resets in the Back Office. Verify actual provider reset and quota rules during account setup; if they cannot be modeled correctly, do not silently treat them as calendar days or months.
- Show each provider's last successful SMTP acceptance and last observed authentication failure with timestamps, without storing or revealing credentials. These are observations, not a live health guarantee or proof of delivery. Brevo can deactivate an SMTP key after 90 days without a successful send; surface last successful send. Keys are created without a fixed expiry (Resend keys never expire), so no expiry date is stored. Keep-alive is generic across Services: one API endpoint, `POST /v1/services/keep-alive`, protected by a secret header token (`API_KEEP_ALIVE_TOKEN`, never shown in the Back Office), runs the keep-alive of every Service that defines one; MAIL is the only one now, and a future Service adds its own keep-alive behind the same endpoint, with no new route or schedule. MAIL's keep-alive sends one email to the owner's address through each enabled provider that had no successful send in the last 30 days, through that provider only (never failing over), reserved and counted against its quota like any send. The answer lists, per Service and provider, `skipped`, `sent`, `rejected` or `unavailable`. The Workflow service (n8n) calls it daily at 03:00 Europe/Rome; the workflow is versioned in `vps/workflows/` with a line in `vps/workflows.sh`, names the existing error workflow, and sends a Telegram message when any result is `rejected` or the call fails. Daily, not monthly, so a failed run is retried the next day, long before the 90 days. An authentication refusal is a definite rejection: mark the provider unavailable and move on to the next provider in slot order. Provide a provider-specific Admin test-send button that sends a real email through the chosen provider, reserves and counts its quota using the same safety rules, and clearly reports accepted, rejected, uncertain, or unavailable results without exposing secrets. A test does not fail over to a different provider.
- Rotating an expired secret normally replaces the value of its existing numbered environment variable and redeploys the API; a new variable or slot is not required. Keep provider identity and usage unchanged. Account for production secret provisioning and avoid logging values.
- Skip disabled, unconfigured or exhausted providers. On a definite rejection, move to the next provider; do not automatically retry an ambiguous timeout. If none is available, surface an appropriate temporary failure and log a sanitized operational event. Never silently claim a verification or reset email was sent when a synchronous failure is known; check Better Auth's real background behavior and anti-enumeration guarantees before choosing responses.
- Provider quotas may reset in different time zones or use rolling periods. Do not assume UTC matches a vendor. Store and validate a provider's reset policy (initially a configurable daily time zone, if supported by the chosen provider), show the period and next reset, and verify actual vendor rules during setup. Limits are operator safety thresholds, not proof of vendor availability or cost.
- Provider changes must not reset or bypass already consumed quota; keep stable provider identity across edits and preserve usage history. Define behavior for limit decreases, disabled services, missing configuration, clock boundaries and concurrent configuration edits. Use a Version for stale saves in line with ADR 0028.
- Password reset is available for existing Users. Verification integration must not lock existing unverified Users out accidentally: explicitly test migration and choose a safe rollout policy before enabling mandatory verification. Registration remains closed for every App. Preserve Better Auth's anti-enumeration behavior, token expiration, trusted callback origins and Session revocation semantics.
- User creation and editing in the Back Office offer an Admin a toggle to require email verification when needed; the default for a newly created User is verified. Preserve existing Users' current verification state during rollout. Saving the toggle does not send email or end existing Sessions: an unverified User receives a verification link on their next sign-in attempt, then signs in after verification. Provide a resend option and test delivery failures and active Sessions.
- Verification links expire after one hour, and the User can request a new one. Do not mention the one-hour duration in the verification screen copy; provide a clear recovery path when a link expires. A successfully verified status persists unless an Admin requires verification again or the email changes. Test expiration and resending against the installed Better Auth behavior.
- The installed Better Auth 1.5.3 verification token is a signed JWT tied to email and expiry, not to the Admin's latest verification decision. An unexpired link issued before an Admin re-requires verification can mark the User verified again. Design and test an atomic invalidation/version check at the actual verification boundary before enabling the toggle; a pre-check that races with the Admin edit is insufficient. Keep Better Auth's origin and token validation intact.
- The installed Better Auth requires `emailAndPassword.requireEmailVerification` and `emailVerification.sendOnSignIn` for the agreed automatic verification email after a correct password. Check callback behavior and prove the closed Registration and existing Session requirements against the installed version, rather than assuming global verification can be enabled safely. After a successful password reset, revoke all of the User's existing Sessions, as the user chose. Better Auth leaves them intact by default; enable its reset revocation option and verify the installed version's behavior. The five-minute Session cookie cache can outlive deleted database Sessions, so ensure protected server-side operations immediately refuse revoked Sessions, including cached cookies, and verify every affected access path. Clear any client-side cached private data as appropriate; already displayed data cannot be recalled.
- Authentication-related responses must preserve account-enumeration protection even on mail failure, quota exhaustion or throttling. The provider's SMTP acceptance can mean queued rather than delivered: Brevo and SMTP2GO document queues at their free-tier daily limits. Never interpret acceptance as inbox delivery or treat a timeout as confirmed rejection.
- Treat Admin-configurable SMTP endpoints as outbound network access: validate endpoint and transport configuration and establish an explicit deployment-safe egress policy, including DNS resolution and redirects, before accepting arbitrary destinations. Enforce authorization on server actions and API routes. Never place verification or reset tokens in request logs, traces, preview data or error reports; audit existing access logging and callbacks as well as the new mailer.
- Place the verification toggle immediately under Roles in the Back Office User create and edit forms, using the existing Role toggle styles. Limit email requests to five per email address in any rolling hour, shared across verification and password reset, including resend and sign-in-triggered sends. Keep the existing general IP limiter; do not add a separate email-specific IP limiter initially. Enforce the agreed limit server-side, separately from provider quotas, with anti-enumeration responses. If the per-address limiter is unavailable, temporarily refuse email requests without sending, using an account-independent response.
- The API already has a general IP-based limiter (defaults 100 requests/minute, configurable) and a separate sign-in/sign-up/change-password limiter (defaults 10 requests/15 minutes); the latter does not currently cover the reset or verification request routes. Both use Redis and fail open when it is unavailable; the new per-address mail limiter deliberately fails closed as agreed above. Do not claim a per-address limiter prevents exhaustion across many different addresses. Normalize addresses consistently and avoid retaining raw addresses in rate-limit keys. The existing fixed-window store permits a boundary burst, so use a rolling window or equivalent to enforce the agreed limit.
- Provider reset evidence: Brevo documents a daily reset but the referenced free-plan documentation does not specify its exact boundary; SMTP2GO says the monthly reset date is shown in the account dashboard and documents daily queuing; Resend's Usage API example exposes daily and monthly `resets_at`, but requires a full-access API key. Confirm actual account-specific windows without assuming the example's dates apply universally; do not add full-access credentials solely for this feature without a separate decision. Until a window is confirmed, mark it unknown and do not present a guessed reset time or rely on a guessed reset for quota enforcement.
- Follow the layout and naming rules in the current guides: a feature with several peer files puts each in its kind folder (`constants/`, `utils/`, `hono/`, a CLI in `utils/`); every new route is named in its owner's `PATH` object and filled with core's `fillPath` (`openApiPath` in the spec), never a literal or a `.replace` on `:id`; paths to the repo root or another package come from config's `REPO` (`@allonfire/config/local/repo`), never `..` from `import.meta`.
- ADR 0019 governs App Registration settings in code; operational provider settings are separate and do not change it. ADRs 0007, 0008 and 0016 govern shared schemas, Liquibase and package ownership. No secrets in a Service table.

## Implementation design (reconciled with the code on 2026-11-03)

- **Schema `service`** (`prisma/schema/service.prisma`): `Service` (`name` enum `ServiceName { MAIL }`, unique; `enabled`), `ServiceProvider` (`slot` unique per Service and ≥ 0; `name`, `enabled`, `host`, `port`, `username`, `fromAddress`, `dailyLimit` ≥ 0, `monthlyLimit` ≥ 0 or null, `dailyResetTimeZone` or null, `lastAcceptedAt`, `lastAuthFailureAt`, `updatedAt` for its Version) and `ServiceUsage` (one row per reservation: provider, `reservedAt`, `status` enum `UsageStatus { RESERVED, ACCEPTED, UNCERTAIN, RELEASED }`, `purpose`). Every row but `RELEASED` counts, so a crash (`RESERVED` forever) consumes capacity conservatively.
- **Quota windows without guessed resets:** the daily window is the calendar day in `dailyResetTimeZone` when an Admin confirmed one, otherwise the rolling last 24 hours; the monthly window is the rolling last 31 days. A rolling window at least as long as the provider's period can never exceed its limit inside any of the provider's periods, so an unknown reset stays safe; the Back Office shows "rolling" instead of a reset time. Usage rows are kept; pruning rows older than 31 days is left for later.
- **Atomic reservation:** one transaction locks the provider row (`SELECT … FOR UPDATE`), counts both windows and inserts the usage row only when both have room, so parallel API instances serialize on the row.
- **Egress policy:** an Admin edits only non-secret settings; the SMTP host comes from a fixed allowlist in code (`MAIL.SMTP_HOSTS`: Brevo's and Resend's relays) and the port is 465 or 587 with TLS required, so no Admin input can reach a private or metadata address. A new provider host is a code change.
- **Outcome rules (nodemailer):** an SMTP reply code (`responseCode`) or a failure before the connection is up (`command` `CONN`, `EDNS`, `ECONNECTION`) is a definite rejection: release the reservation and try the next slot; `EAUTH`/535 also sets `lastAuthFailureAt`. Anything else (a timeout after `DATA`, an unknown error) is uncertain: keep the reservation as `UNCERTAIN` and stop.
- **Mail is a core feature** (`packages/core/src/features/mail/`, as the owner chose, not a package of its own): its constants (the host allowlist, outcomes), the provider selection and failover (`sendMail`, generic over the purpose a store records), the nodemailer transport and `MAIL_PROVIDER_<slot>_KEY` (`environment/mail-environment`, read when sending). Core cannot import the database (the database imports core), so the database-backed store lives in the API (`features/mail/database-store`), beside the auth-email boundary. Templates are React Email components in `packages/ui` (`features/email/`), rendered server-side.
- **Better Auth:** `createAuth` takes an optional `mail` from the host. Sending runs through `advanced.backgroundTasks`, so a response never waits on SMTP and timing does not reveal an account. The reset email links straight to the App's reset page (`redirectTo?token=…`), never to the API's `GET /reset-password/:token`, whose path the request log would record. The per-address limit is a Redis sorted set keyed by a hash of the normalized address; when Redis cannot answer, `hooks.before` refuses `/request-password-reset` and `/send-verification-email` with a 503 before any lookup, and a sign-in by an unverified User still answers `EMAIL_NOT_VERIFIED` without sending.
- **Stale verification links:** `User.verificationRequiredAt` is set when an Admin requires verification; on `/verify-email` the `user.update.before` hook replaces Better Auth's write with one conditional `UPDATE … WHERE "verificationRequiredAt" IS NULL OR "verificationRequiredAt" <= <token iat>`, so whichever commits first, an older link never satisfies a newer requirement.
- **Rollout:** every existing User is already verified (`createUser` and the seed set `emailVerified: true`; Google verifies its own), so turning on `requireEmailVerification` changes nobody's state.
